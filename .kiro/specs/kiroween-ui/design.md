## Approach

Presentation only. Each app keeps its `ui/app-view.ts` structure and controllers; the redesign changes markup structure around existing elements, CSS, a static SVG sprite, and a few small pure view helpers. No controller, package, service worker or precache change. Shared tokens and shared component styles live in the byte-identical `styles/ghostsync-theme.css`; app-specific layout lives in `patchboard-ui.css` and `fieldledger.css`.

Direction: "illustrated midnight field guide". Ink-purple surfaces, warm paper panels, Kiro-inspired violet (hue only), lantern amber for the single warm accent and the focus ring on dark surfaces. A crescent moon, torn-paper edges and a dotted flight path are the only decorative motifs. Display type (system serif stack) appears only in the hero headline; everything else is system sans.

## Components

### 1. Courier symbol set (static, shared)
A hidden `<svg id="gs-sprite" aria-hidden="true" focusable="false" width="0" height="0">` in each app's `index.html` defines `<symbol>`s: `gs-courier` (hero pose), `gs-courier-sm` (offline pose), `gs-courier-step-scan|review|import` (three step poses), `gs-moon`, `gs-phone`, `gs-laptop`, `gs-capsule`. Symbols use `currentColor` plus palette custom properties so one set renders on ink and on paper. Why static: the CSP and the PatchBoard dist scan (`createElementNS` namespace string would add a second `https?://` URL) rule out building SVG nodes in JS; the `h()` helper cannot create SVG elements. Dynamic places that need an icon use a small helper `ui/icon.ts` that sets `innerHTML` on a `<template>` from a constant string `<svg class="gs-icon" aria-hidden="true" focusable="false"><use href="#gs-courier-sm"></use></svg>`; the HTML parser supplies the namespace, so no namespace string appears in JS. Fallback if `<use>` of an in-page sprite is not acceptable to a scan: put the markup in the static HTML and toggle with `hidden`/CSS.
No emitted SVG files are planned, so no precache entries are planned; if any file ends up under `dist/assets`, the unchanged plugin lists it and KW-DIST-ASSETS asserts it.
The sprite block is byte-identical in both apps (KW-UNIT-SPRITE-PARITY compares the text between the `<!-- gs-sprite:start -->` and `<!-- gs-sprite:end -->` comments).

### 2. Hero (PatchBoard join view, outside `<main>`)
`section.pb-hero` containing: `.pb-hero-art` (inline SVG scene: phone and laptop silhouettes, dotted flight path, crescent moon, courier mid-flight; torn-paper edge as `clip-path` on the paper panel behind the form), `.pb-hero-copy` (display-type headline as `h2` or `p.pb-hero-title`; supporting line), and the existing join `form` (label `Board ID`, input `#board-id` with placeholder and `aria-describedby="board-rules board-preview board-error"`, hint, `Open board`), plus the `See how it works` button. Layout: CSS grid, two columns from `min-width: 56em` (copy and form left, art right), one column below. In the stack the art is a compact strip (height `clamp(96px, 18dvh, 150px)`), placed above the headline, so the form's bottom edge stays inside the viewport.
Vertical budget at 390x664 (planned numbers, to be measured, not trusted): header 52, readiness cue 36, art 120, headline 2 to 3 lines at 28px/1.1 about 92, supporting line 2 lines about 44, label+input 76, button 48, gaps 40 = 508 of 664, leaving about 150 for Safari toolbar slack and the first-visit notice (about 56). At 320x480 the budget is exceeded by a small amount; the art is hidden on short screens so the action stays within reach (as shipped: `@media (max-height: 36rem)`, i.e. 576px, not the planned 520px; corrected in the PR-preview check). At a visual viewport of 26rem (416px) or less, which is how the keyboard-open emulation and a landscape phone look, the supporting line is hidden and the headline is smaller so the field and the button get the room (added in the PR-preview check). Hiding art by media query changes no accessibility tree (it is `aria-hidden`).
Heading levels: the single `h1` stays in the header. The headline is `h2.gs-hero-title` (shared class in both apps; the planned name `pb-hero-title` was not used; corrected in the PR-preview check). Existing `h2` "Open a shared board" (join form heading) becomes the visually hidden label of the form region and keeps its text so heading queries still hold.
Rules paragraph `#board-rules` ("Everyone who shares this board types the same ID. ...") is kept, collapsed into a quiet helper line under the field; `#board-error` and `#board-preview` are unchanged.

### 3. Readiness once
One visible cue, derived from the existing elements without changing their text or attributes.
As shipped (corrected in the PR-preview check; the table below is the original plan): while online, the visible cue is `offline-indicator` in every offline-readiness state, ready or not. While offline it is the banner. `network-chip` and `#status-note` are always visually hidden (1px clip) and stay in the DOM with their exact text. E2E-KW-PB-05 and E2E-KW-FL-04 assert exactly this: `["offline-indicator"]` online, `["offline-banner"]` offline, `["offline-indicator"]` before offline-ready. Original plan:

| Element | How it is satisfied |
| --- | --- |
| `network-chip` | In DOM at all times with exact text `Network: online|offline`. When the readiness cue is the visible one, this node is the visible chip (it keeps its exact text; the icon is CSS `::before`). |
| `offline-indicator` | In DOM with exact state copy and `data-offline-state`. Rendered visually hidden (clip, 1px, not `display:none`) while `network-chip` is the visible cue and the indicator is `ready`; visible as the status line while not ready (registering, installing, waiting, failed) because it is then the one actionable message. |
| `first-visit-notice` | Unchanged: `hidden` property toggled by `AppView` as before; visible text exact. |
| `#status-note` | In DOM, plain connection text from `status-text.connectionNote`; visually hidden while the banner (section 5) is the visible cue, visible otherwise. |
| `transfer-mode` | Exact text, small chip in the workspace transfer area; present on join. |
At any moment the visible readiness cue is exactly one of: chip (online ready), indicator line (not ready), banner (offline). E2E-KW-PB-05 counts visible readiness elements with a locator list and expects 1.

### 4. Header
`header.gs-header`: mark, wordmark "GhostSync", `h1` app name, `#gs-header-actions` (Help). Height at most 56px at 390 wide. No tagline.

### 5. Offline banner (single compact element, space reserved)
A `div.pb-offline` rendered once under the header in a fixed-height slot (`min-height` equal to the banner height, `visibility: hidden` and `aria-hidden` when online so layout never moves). It becomes visible when `AppView`'s existing `online` state (already driven by `window` `online`/`offline` events and `navigator.onLine`) is false. Copy: `The network vanished. Your work didn't.` plus the courier and a one-line state from a new pure helper `offlineBannerView(online, phase, saveState)` in `ui/offline-banner.ts` (unit tested): saved path `Changes still save on this device.`; error or recovery path `Changes are NOT saved to this device.` (the banner never says saved when `saveState === "error"` or `phase === "recovery"`). `#status-note` text is unchanged and remains the asserted plain text. The banner is not a live region (the existing `network-chip` and `#status-note` content are already the announced surface); it carries `role="group"` with an `aria-label` only if needed for naming, and a single `aria-hidden` courier.
Lantern reaction: one CSS animation (`@keyframes gs-lantern` in the shared theme, as shipped; planned as `pb-lantern`; 800 ms, `animation-iteration-count: 1`, `animation-fill-mode: both`) on the lantern part of the courier inside the banner, started by adding class `is-reacting` when the real offline event fires (the existing `AppView` offline callback) and removed on `animationend`; the settled state is static. Reduced motion: the shared block sets `animation: none !important; transition: none !important`, so `getAnimations()` is empty and the text carries the state.

### 6. Workspace (PatchBoard)
Order inside `<main>`: workspace header (board name, `save-indicator`, `Share`, `Import`, `Change board`), Add card form (kept as a section named by `add-h`; moved visually into the To do column header area on wide screens by grid placement, DOM order unchanged), board (`#board`, columns with count badges next to the `h3`), incomplete cards, transfer. `Share` and `Import` are `button type="button"` that scroll to and focus existing targets: as shipped, `Share` focuses the Transfer heading `#transfer-h` (`tabindex=-1`), not `qr-show-btn`, and `Import` focuses `#import-file` (corrected in the PR-preview check); they hold no import logic and their names ("Share", "Import") contain none of the reserved substrings. Counts: a sibling `span.pb-count` after the heading text, so heading names stay "To do", "Doing", "Done". Torn-paper header edge is a `::after` clipped layer with `pointer-events: none`.

### 7. QR sender stage
`.pb-stage` (paper frame) around `.gs-qr-frame` (pure `#fff` stage) around `canvas[data-testid=qr-canvas]`. The canvas already contains the 4-module quiet zone; the white frame adds no overlay. No effect properties on the canvas or any ancestor; decorative flourishes are siblings with `pointer-events: none`. Details line (bytes, version, checksum, board) stays in the existing exact-text elements. When `too-large` or `too-narrow`, the existing message stays. The Export control itself stays in the file area of the same Transfer section. As shipped after the PR-preview check, a `Go to file export` button (`data-testid=qr-file-instead`) sits directly under the message in the show panel and moves focus to `Export capsule (.gscap)`. It is visible only in those two states. Presentation only: the message text, the QR limits, `chooseScale` and the controller are unchanged.
Narrow threshold (PR-preview check decision): the view passes `qr-transfer.clientWidth - 88` (`QR_CHROME_PX`, the padding of the panel plus the white frame) to the unchanged `chooseScale`, which needs (modules + 8) x 4 CSS px (qr-transfer AC-QR-004-3: integer scale of at least 4). A 568 to 658-byte board is version 18 (89 modules, 97 with the quiet zone), so it needs 388 px for the code alone. A 390 px portrait phone has about 390 - 32 (page padding) - 88 = 270 px, and the whole viewport is narrower than 388 px. Measuring the viewport instead of the panel would still give too-narrow. A phone in landscape (844 px wide) can draw it. So too-narrow at 390 px portrait is correct under the existing rule, and the threshold was kept.

### 8. QR receiver steps
`ui/qr-steps.ts` exports `qrStepsView(state: string): { active: 1|2|3|0; done: number; error: boolean }` as a pure map from the existing `data-qr-state` values. `qr-view.ts` renders `ol.pb-steps` with three `li` (`data-step`, `data-step-state="pending|current|done|error"`, text label plus an icon, courier variant per step) and updates it from the same state the view already sets on `qr-scan-panel`. It is a presentational mirror: it never calls the controller and never invents a state. After `scanned`, the board name from `qr-meta-document-id` is repeated in the step caption as text only if the existing element is not already visible; the existing `qr-import-btn` and `qr-discard-btn` and the trust warning stay in place. Result: `import-result` and `merge-summary` text come from the existing `status-text.importHeadline` and save outcome; the new result card adds one outcome line derived from `data-import-state` only. As shipped it reads `Saved on this device.` or `Not saved to this device yet. Use Retry save.` (`p.gs-result-state` inside `merge-summary`; corrected in the PR-preview check). The not-saved alert heading is the existing `Capsule applied, but NOT saved to this device`.
The steps list adds no focusable element and no `role=alert`; its `ol` is inside `qr-scan-panel` after the controls so DOM tab order Show, Hide, Scan is unchanged.

Offline banner, readiness-once, `See how it works`, Help and credit as PatchBoard with FieldLedger copy. `[hidden]` rule remains from the shared theme.

### 10. iPhone and safe area
`<meta name="viewport" content="width=device-width, initial-scale=1, viewport-fit=cover">` added only together with `padding: max(16px, env(safe-area-inset-left))` style rules on `body`/`.gs-page` (all four edges) and `padding-bottom: max(16px, env(safe-area-inset-bottom))`. `min-height: 100vh; min-height: 100dvh` fallbacks. No `position: fixed` or `sticky` element sits over controls; decorative fixed layers (if kept) are `pointer-events: none`, `aria-hidden`, and clipped. At 320 px the 16 px page padding is kept so `qr-transfer` stays under the empty-board code width (contracts hazard: too-narrow at 320). Keyboard: no JS; the layout keeps `Open board` directly under the field so the browser's own focus scroll-into-view reveals both; E2E-KW-PB-03 asserts reachability after shrinking the viewport.

### 11. Motion
Only three animations exist: the single 800 ms lantern flicker, an optional one-shot fade of the See-how-it-works reveal (disabled by the reduced-motion block), and a step-completion tick (one-shot). All are inside the shared reduced-motion block (`animation: none !important; transition: none !important`). No looping animation exists anywhere, so there is never a running animation after the reaction ends.

## Failure and edge behaviour

- Storage denied, camera denied or absent, service worker unavailable: unchanged (existing states, banners and copy). The new views read states; they never change them.
- Reduced motion and forced colours: state is carried by text or icon; the hero art is `aria-hidden`.
- A very small height (below 520px): art hidden, action first.
- SVG sprite unsupported: the layout still works; icons are decorative.
