# sdk-foundation — Requirements

> GhostSync Kit (`@ghostsync/kit`) — Requirements-First Feature Spec.
> Branch: `feat/sdk-foundation`. This document covers requirements only. Design and tasks are authored alongside it and reviewed together at the design-and-tasks gate. Implementation begins only after that review gate passes.
>
> **Verified baseline:** commit `ab37419` — a browser-compatible scalar `Y.Map` wrapper around Yjs, full-state binary updates carrying a separate `documentId`, fresh-replica restoration with a new session `clientID`, lifecycle guards (post-`destroy` throws, idempotent `destroy`), and **37 passing tests including six fast-check properties** (seed `424242`, 200 runs each). The prior `core-sync-proof` was independently verified. This spec builds **additively** on that baseline; nothing below weakens or removes existing behavior or coverage.
>
> **Architecture-correction revision (revision 4).** An independent reviewer reproduced three real Yjs `13.6.33` behaviors that invalidated the previously-approved nested-`Y.Map` data model and two prose claims. The corrections are folded in below and are consistent across `requirements.md`, `design.md`, and `tasks.md`:
> - **Defect A (nested-map identity):** two replicas that each independently do `parent.set(id, new Y.Map())` offline do **not** converge to one shared nested map — one side's fields are lost after sync. The data model is therefore **flat composite keys**, never independently-created nested maps.
> - **Defect B (full-rewrite clobber):** rewriting *all* fields of an entity overwrites a concurrent edit to a *different* field. `put` is therefore a **changed-fields diff** that writes only the leaf keys whose values actually changed.
> - **Defect C (no-op still fires `afterTransaction`):** applying an empty no-op update fires `afterTransaction` **once** and the `update` event **zero** times. Observable change notifications are therefore derived from the **actual key deltas**, not from whether a transaction event fired.
>
> **Revision 5 (MEDIUM-1 correction — two separate top-level maps).** The architecture-correction review (`.review/spec-correction-verdict.json`) returned `CHANGES_REQUESTED` with 1 MEDIUM and 2 NITs. Revision 4 stored the flat composite keys in the **same** top-level `root` `Y.Map` as the legacy scalar keys and needed a bare-vs-structured discriminator so `getState()` would project only legacy keys; the reviewer's MEDIUM-1 found that discriminator self-contradictory and undefined where a legacy user key is byte-identical to a structured key. This revision removes the discriminator entirely by using **two separate top-level shared maps in the same `Y.Doc`**: `doc.getMap("root")` keeps the legacy scalar keys exactly as the `ab37419` baseline (every key projected by `getState()`, no key reserved or rejected), and `doc.getMap("ghostsync:records:v1")` holds the structured composite-key records (all sentinels/escaping scoped inside it). **Map membership decides** which API owns a key — there is no key-shape predicate anywhere. Both maps live in one `Y.Doc`, so full-state and differential exports carry both automatically.

## Summary

Turn the verified `core-sync-proof` into a reusable SDK foundation that two genuinely different applications — **FieldLedger** (offline incident reporting) and **PatchBoard** (offline kanban) — can build on without reimplementing any sync logic. The foundation adds, on top of the existing scalar-`Y.Map` replica:

1. A **typed application-adapter contract** that separates each app's schema and validation from the shared synchronization engine.
2. A **structured data model built on flat composite keys** inside a **second, dedicated top-level `Y.Map` named `ghostsync:records:v1`** (the legacy `root` map is left untouched) — a collection/entity/field address is encoded into one leaf key, so real app records are represented without opaque JSON blobs **and** without independently-created nested maps (which lose data under concurrent offline creation — defect A). Field-level CRDT merge with explicitly-stated conflict limitations. Both maps belong to one `Y.Doc`, so exports carry both.
3. A richer **identity** model distinguishing the logical `documentId`, the application/schema identity and version, the Yjs session `clientID`, and a local persistence identifier.
4. **Incremental synchronization** (state-vector export + differential update generation) alongside the existing full-state export.
5. **Lifecycle notifications** (local-change, remote-change, unsubscribe, destroy) whose observable-change signal is derived from the real key deltas of each transaction, with transaction/origin tagging that prevents sync feedback loops.
6. A small **transport-neutral update contract** that file and QR transports will later consume — without building any transport, capsule, checksum, or UI in this milestone.
7. **Validation and error** responsibilities for local writes, adapter/schema compatibility, document mismatches, malformed updates, and the state-vector/update carrier boundary, with a precise, honestly-bounded statement of what a rejection guarantees about the live document.

This milestone is still a **Node in-memory SDK foundation**. It is distinct from — and must not entangle with — browser IndexedDB persistence, service workers, offline app loading, file/QR capsules, checksums, and UI, all of which remain future work. **Browser compatibility is a build-time requirement** (no `node:` imports in `src`, library compiled without DOM libs); it is explicitly **not** a claim of browser-executed evidence — a no-`node:`-imports source scan is a useful static check, not proof of browser runtime behavior, and actual browser execution evidence remains **pending**. The proof suite stays Node in-memory.

The requirements align with workspace steering:

- **Product** — all sync logic lives only in the Kit; FieldLedger and PatchBoard consume the Kit's public API. File transfer is the first transport tier; the transport-neutral contract here is what that tier will consume.
- **Architecture** — Yjs is the CRDT layer; each replica is independent; merge is a pure function of updates; storage and transport stay pluggable and separate from merge logic; IndexedDB persistence and offline loading stay separate concerns and are out of scope here.
- **Coding** — strict TypeScript, no `any` by default; versioned public interface, private internals; minimal dependency graph (no new dependency is added); existing behavior preserved behind tests.
- **Testing** — actual test outputs required; convergence, duplicate-import safety, update ordering, persistence-after-reload (in-memory surrogate), invalid-input rejection, and offline behavior are all covered; property-based tests cover merge invariants.
- **Security** — every update is untrusted; size is bounded before decoding at the capsule tier (deferred) and carrier shape is validated before decoding here; the transport-neutral carrier is integrity-scoped only; caller-supplied metadata does **not** authenticate bytes or senders; a checksum detects corruption, it does not authenticate the sender; size bounds, capsule versioning, and checksums remain the capsule tier's job and are out of scope here.

## Definitions

These apply to every requirement and acceptance criterion below.

- **Entity.** One record in a document — e.g. a FieldLedger incident or a PatchBoard card. It has no object of its own in the CRDT; it exists exactly as the set of **field leaf keys** that address it (see *Composite key*). "Creating" an entity is writing its field keys; an entity "exists" iff at least one of its field keys is present.
- **Field.** One scalar-valued leaf key. A **scalar** is a `string`, a finite `number` (not `NaN`, not `±Infinity`), a `boolean`, or `null` — unchanged from the baseline.
- **Collection.** A named namespace for entities of one schema inside a document. A collection is not a container object; it is the first segment of every composite key it owns (inside the records map), so two collections that both hold entity id `"1"` never share field keys. The collection identifier is a DETERMINISTIC, collision-safe encoding of the adapter's `(app, entityType)` tuple — `collectionId = esc(app) + SEP + esc(entityType)` (clarification 1) — so two distinct tuples can never encode to the same collection string. `schemaVersion` is NOT part of the collection identifier (it is recorded in the persisted schema meta key, not a namespace discriminator), so bumping the version does not silently open a separate namespace; instead a version change is detected as a schema mismatch on open/recheck.
- **Legacy map (`root`).** The baseline top-level `Y.Map` named `root`, holding the scalar keys written by `replica.set`. Its name, contents, and encoded structure are unchanged from the `ab37419` baseline. Every key in it is a legacy key; no key in it is reserved, rejected, escaped, or reclassified.
- **Records map (`ghostsync:records:v1`).** The second, dedicated top-level `Y.Map` in the same `Y.Doc`, holding the structured composite-key records (field leaf keys and reserved meta keys). All structured-key sentinels and escaping are scoped **inside** this map; they never affect the legacy map.
- **Composite key.** The single flat string key under which one field is stored in the **records map** (`ghostsync:records:v1`). It encodes, in order, a reserved structured-key sentinel, the collection name, the entity id, and the field name, each separated by a reserved unit separator and each segment escaped so a name containing the separator or the sentinel cannot forge another address (see `design.md` § Storage layout). Because composite keys live in a different map from legacy keys, a legacy key and a composite key with the same string are two unrelated values; neither can collide with or shadow the other.
- **Document.** The whole collection of entities for one logical `documentId`, held in one `Y.Doc` as two top-level `Y.Map`s of leaf keys: the legacy `root` map and the `ghostsync:records:v1` records map.
- **Baseline observable state.** The **fresh** flat snapshot returned by `getState()`: a null-prototype object mapping **every** key in the `root` map to its scalar value, exactly as the baseline promised (no filtering, no sentinel inspection). `getState()` is the FLAT baseline projection of the `root` map and SHALL NOT be redefined to return all structured entities, and SHALL NOT exclude any `root` key. Structured snapshots are read through `Collection#get`/`Collection#list` against the records map. Comparison is **deep equality** (`expect(...).toEqual(...)`), never reference identity and never byte-for-byte equality of encoded Yjs bytes. Deep equality stays a test concern; no runtime deep-equality helper lives in `src`.
- **Adapter.** A typed, app-supplied object (`EntityAdapter<T>`) that declares an application/schema identity + version and provides `validate`/`toFields`/`fromFields` for one entity type. The engine never imports an adapter; the consumer wires it in.
- **State vector.** `Y.encodeStateVector(doc)` output describing what a replica already has; the basis for differential updates. It is a value a **future transport** may carry between replicas, not inherently a same-process value; at `applyUpdate` it is untrusted input.
- **Differential update.** `Y.encodeStateAsUpdate(doc, remoteStateVector)` output carrying only operations the remote replica is missing.
- **Update carrier.** The transport-neutral `{ documentId, bytes, kind }` value defined in REQ-SDK-006. The existing baseline carrier `{ documentId, bytes }` remains valid and is a subtype view of this.
- **Origin.** The Yjs transaction `origin` tag the engine stamps on every mutation (`LOCAL_ORIGIN` for local writes, `REMOTE_ORIGIN` for applied updates). Notifications carry the origin so consumers never re-broadcast applied-remote changes (no feedback loop).
- **Observable change.** A transaction that actually altered at least one leaf key of **either** top-level map — the `root` map or the `ghostsync:records:v1` records map (an add, update, or delete in the transaction's key-delta for either map, read via `transaction.changed.get(map)`). A transaction that fired `afterTransaction` but changed no key in either map is NOT an observable change and SHALL NOT notify subscribers.

## Functional Requirements

### REQ-SDK-001 — Typed application-adapter contract separates schema from engine

The Kit exposes a typed adapter contract so an application declares its own schema, validation, and field mapping without the engine knowing any app-specific types. Two genuinely different schemas — a FieldLedger incident and a PatchBoard card — are each expressible through the same contract, proving the engine is schema-agnostic.

**Acceptance criteria**

- AC-SDK-001-1: WHEN an application defines an `EntityAdapter<T>` with an `app` identity, a `schemaVersion`, an `entityType`, and `validate`/`toFields`/`fromFields` functions, THE SYSTEM SHALL accept it and expose a typed `Collection<T>` whose `put`/`get`/`getResult`/`list`/`listResults`/`delete`/`has` operations are typed in terms of the app's `T` (where `put(id, entity)` is create-or-overwrite with changed-fields semantics per REQ-SDK-003A, and `listResults()` enumerates every stored id — including invalid records — as `[id, GetResult<T>]` tuples per REQ-SDK-001/007) without the engine referencing any app-specific type.
- AC-SDK-001-2: WHEN a value produced by `toFields(entity)` contains any non-scalar field value, THE SYSTEM SHALL reject the write by throwing a `TypeError` before mutating the document (field values must be scalars; nested structures are not allowed as field values).
- AC-SDK-001-3: WHEN the same running engine is used by a FieldLedger incident adapter and a PatchBoard card adapter, THE SYSTEM SHALL support both schemas with no engine code change, demonstrating two genuinely different schemas (distinct `entityType`, distinct fields, distinct validation) over one SDK.
- AC-SDK-001-4: WHEN `fromFields(fields)` is called on a stored entity's projected fields, THE SYSTEM SHALL return a typed `T` reconstructed from the scalar fields, round-tripping a value written with `toFields`. The engine SHALL run `fromFields` + `adapter.validate` on READS (`get`/`getResult`/`list`): a complete/valid record reconstructs normally; an INCOMPLETE or invalid record (e.g. a field deleted concurrently with an edit) is a CONTROLLED outcome — `getResult(id)` returns `{ ok:false, reason:"invalidRecord", id, fields }` and `get(id)` throws a stable `IncompleteRecordError` — and SHALL preserve the underlying stored fields (never manufacture missing fields, never delete fields on a failed read, never cast an invalid record to a valid `T`). `list()` skips invalid records rather than throwing. Entity-wide business deletion policy is future app-layer work (out of scope).

### REQ-SDK-002 — Flat-composite-key data model with field-level merge; no independently-created nested maps

Structured records live in a dedicated top-level `Y.Map` named `ghostsync:records:v1` (separate from the legacy `root` map, both in the same `Y.Doc`); every entity field is a flat composite leaf key inside the records map. Whole application documents are never stored as opaque JSON strings, and entities are never represented as independently-created nested `Y.Map` objects (defect A: two replicas each doing `parent.set(id, new Y.Map())` offline do not converge to one shared map). Concurrent "creation" of the same entity id is just concurrent sets of sibling leaf keys, which merge field-by-field. Concurrent edits to different fields of the same entity both survive; concurrent edits to the same field resolve to exactly one submitted value (last-writer-wins at field level per native Yjs); deletion and edit-concurrent-with-deletion follow stated, tested rules.

**Acceptance criteria**

- AC-SDK-002-1: WHEN two replicas each create and edit entities and exchange updates, THE SYSTEM SHALL converge both replicas to deeply equal structured snapshots (via `Collection#list`) in which every entity is a set of scalar fields (not a single opaque JSON string, not a nested map object).
- AC-SDK-002-2 (concurrent different-field edits): WHEN replica A edits field F1 of entity E and replica B concurrently edits a different field F2 of the same entity E, and updates are exchanged both ways, THE SYSTEM SHALL preserve **both** edits on both replicas (F1 = A's value and F2 = B's value), because F1 and F2 are distinct sibling leaf keys that merge independently.
- AC-SDK-002-3 (same-field conflict): WHEN replica A sets field F of entity E to value X and replica B concurrently sets the same field F of the same entity E to value Y (X ≠ Y), and updates are exchanged both ways, THE SYSTEM SHALL resolve F to exactly one of {X, Y}, identical on both replicas. THE SYSTEM SHALL NOT promise that every conflicting value is preserved — this is a deliberate field-level last-writer-wins limitation; the losing value is discarded, and the winner is determined by native Yjs merge order, **not** wall-clock time.
- AC-SDK-002-4 (concurrent creation of the same entity id): WHEN replica A and replica B each independently create entity id E in the same collection OFFLINE (no server, no pre-sync), writing some fields each, and updates are exchanged both ways, THE SYSTEM SHALL converge both replicas to one entity E whose field set is the per-field merge of both replicas' writes (every distinct field survives; any field written on both sides resolves by AC-SDK-002-3). THE SYSTEM SHALL NOT lose either side's fields (the defect-A guard).
- AC-SDK-002-5 (deletion): WHEN replica A deletes entity E and the update is exchanged with replica B, THE SYSTEM SHALL converge both replicas to a structured snapshot in which entity E is absent. Deleting E on a replica SHALL remove all of E's field leaf keys in the records map in **one local Yjs transaction** (local transaction atomicity).
- AC-SDK-002-6 (edit concurrent with deletion): WHEN replica A deletes entity E while replica B concurrently edits a field of the same entity E, and updates are exchanged both ways, THE SYSTEM SHALL converge both replicas to one identical structured snapshot, and THE SYSTEM SHALL document which outcome native Yjs produces — the fields A deleted stay deleted, and a field B concurrently wrote to a **different** key survives as a resurrected single-field entity (field-level, not entity-level, delete granularity) — rather than promising both the full entity and its deletion coexist. Local transaction atomicity (A's delete is one transaction) is distinct from concurrent-deletion semantics (how that delete merges against B's concurrent field write), and both are stated.
- AC-SDK-002-7 (reused deleted id): THE SYSTEM SHALL support reusing a previously-deleted entity id: because an entity is only its live field keys, writing E's fields again after E was deleted recreates E with the new fields; any field key concurrently deleted-and-rewritten resolves by native Yjs per AC-SDK-002-3. This is the recommended policy (reuse allowed) and SHALL be stated as such.
- AC-SDK-002-8 (projection safety): WHEN state is projected (via `getState()` for the legacy `root` map or `Collection#get`/`list` for structured entities), THE SYSTEM SHALL expose only scalar values and SHALL build each snapshot on a null-prototype object so reserved-looking key names (`__proto__`, `constructor`, `toString`) are preserved as own data properties, consistent with the baseline projection guarantee. `getState()` SHALL project **every** key in the `root` map without filtering (map membership, not a key-shape predicate, keeps structured keys out of `getState()` because they live in a different map).
- AC-SDK-002-9 (name escaping, scoped to the records map): WHEN a collection name, entity id, or field name contains the reserved separator byte or the reserved structured-key sentinel, THE SYSTEM SHALL escape it **within the records-map composite key** so the key is unambiguous and one name can never forge another address. This escaping is internal to `ghostsync:records:v1` and SHALL NOT be applied to, or consulted for, any `root` key; because legacy keys and composite keys live in separate maps, no key-shape classification is ever performed and a legacy key SHALL NEVER be mistaken for a structured key or vice versa.
- AC-SDK-002-10 (legacy/structured key coexistence — collision regression): WHEN a legacy key written via `replica.set` is byte-identical to a structured field key held in the records map for some collection/entity/field, THE SYSTEM SHALL keep the two values independent — the legacy `replica.get`/`getState` SHALL read the legacy value from the `root` map and `Collection#get` SHALL read the structured value from the `ghostsync:records:v1` map — neither shadowing, overwriting, nor dropping the other.
- AC-SDK-002-11 (sentinel-prefixed legacy keys remain valid): WHEN a legacy key written via `replica.set` begins with the structured-key sentinel character, THE SYSTEM SHALL treat it as an ordinary legacy key — `set`/`get`/`has`/`delete` operate on it normally and `getState()` projects it — and SHALL NOT reject, reserve, escape, or reclassify it.

### REQ-SDK-003 — Distinct identity dimensions; schema identity travels with the data; metadata does not authenticate

The SDK distinguishes four identity dimensions and keeps them independent: the logical `documentId`, the application/schema identity + version, the Yjs session `clientID`, and a local persistence identifier. Schema identity is recorded **inside the document** (within the composite-key model) so it survives export/restore and remote import and a mismatch is detectable — not merely held in a process-local first-open registry. Caller-supplied metadata is descriptive only; it does not authenticate the bytes or the sender.

**Acceptance criteria**

- AC-SDK-003-1: WHEN a replica is created, THE SYSTEM SHALL carry a caller-supplied logical `documentId` (string) that is stored separately from all Yjs internals and is never derived from the Yjs `clientID`.
- AC-SDK-003-2: WHEN an adapter declares `{ app, schemaVersion, entityType }`, THE SYSTEM SHALL record that collection's `SchemaIdentity` as a reserved meta leaf key inside the `ghostsync:records:v1` records map on first write, so it is carried in exported bytes (both maps share one `Y.Doc`) and re-derivable on remote import; AND WHEN a collection is opened (locally or after import) with an adapter whose recorded `SchemaIdentity` is incompatible, THE SYSTEM SHALL reject the open with a distinguishable error and SHALL NOT mutate the document. Compatibility SHALL be RECHECKED for an EXISTING `Collection` handle on each operation (clarification 5), not only at the initial open: because `applyUpdate` can import a conflicting `SchemaIdentity` meta value AFTER a handle already exists, an existing handle whose stored meta becomes incompatible SHALL reject its next operation deterministically rather than silently mixing schemas.
- AC-SDK-003-3: WHEN two replicas of the same `documentId` are created, THE SYSTEM SHALL give each a distinct Yjs session `clientID` (fresh per `new Y.Doc()`), and the `clientID` SHALL NOT be used as document identity.
- AC-SDK-003-4: WHEN a local persistence identifier is needed (future storage keying), THE SYSTEM SHALL define it as a separate value derived from `documentId` (not from the `clientID`), documented as a storage-layer concern and not implemented in this milestone.
- AC-SDK-003-5: THE SYSTEM SHALL document that `documentId`, `app`, and `schemaVersion` are caller-supplied metadata that identify intent only; they do **not** authenticate the update bytes and do **not** authenticate the sender. A checksum (future capsule tier) detects corruption; it does not authenticate the sender. Integrity-vs-authentication is verified behaviorally (a wrong-`documentId` carrier is rejected and leaves state unchanged), not by searching comments.

### REQ-SDK-003A — `put` and field edits are a changed-fields diff (no full-entity rewrite)

`put(id, entity)` is create-or-overwrite by **intent**, but it is implemented as a changed-fields diff so it never overwrites an unrelated concurrent edit (defect B). It writes only the leaf keys whose scalar value differs from what is currently stored, deletes leaf keys for fields omitted from the new entity, and leaves unchanged fields untouched (no write).

**Acceptance criteria**

- AC-SDK-003A-1: WHEN `put(id, entity)` is called, THE SYSTEM SHALL validate via the adapter and the scalar guard first (throwing before any mutation on failure), then compute the diff between `toFields(entity)` and the entity's currently-stored fields, and in one local transaction SHALL set only the fields whose value changed, delete the leaf keys of fields present before but absent from `toFields(entity)` (omitted-field removal), and perform NO write for a field whose value is unchanged.
- AC-SDK-003A-2: WHEN replica A and replica B both start with entity E = `{ title: "old", priority: "low" }`, A calls `put` to change only `title`, and B concurrently calls `put` to change only `priority`, and updates are exchanged both ways, THE SYSTEM SHALL converge both replicas to `{ title: <A's value>, priority: <B's value> }` — BOTH intended changes survive, because each `put` wrote only its changed leaf key and left the other field key untouched (the defect-B guard).
- AC-SDK-003A-3: THE SYSTEM SHALL document the omitted-field-removal semantics of `put` (a field absent from the new entity is deleted as a leaf key) so `put` cannot silently retain stale fields, and SHALL state that unchanged fields generate no writes. THE SYSTEM SHALL document that the changed-fields comparison is against the CURRENT LOCAL stored state (clarification 6): a caller passing a STALE full entity can still express an overwrite — any field whose value differs from the current local value is written and wins by field-level LWW — so `put` does NOT and cannot promise stale-form safety.

### REQ-SDK-004 — Incremental synchronization via state vectors and differential updates

Alongside the existing full-state export, a replica can export its state vector and generate a differential update targeting a peer's state vector, so already-synchronized peers exchange minimal bytes. A legitimate no-op differential update is still valid non-empty Yjs bytes; zero-length bytes remain an invalid carrier.

**Acceptance criteria**

- AC-SDK-004-1 (initial sync): WHEN replica B has an empty state vector and replica A generates a differential update against B's state vector, THE SYSTEM SHALL produce bytes that, applied to B, make B's structured snapshot deeply equal A's.
- AC-SDK-004-2 (state-vector export): WHEN a replica exports its state vector, THE SYSTEM SHALL produce a `StateVector` carrier `{ documentId, kind:"stateVector", bytes: Y.encodeStateVector(doc) }` that another replica can pass to differential generation.
- AC-SDK-004-3 (already-synchronized peers → legitimate no-op): WHEN replica A generates a differential update against the state vector of a peer that is already fully synchronized with A, THE SYSTEM SHALL produce a valid, **non-empty** Yjs update carrier whose application to that peer leaves the peer's observable state unchanged. THE SYSTEM SHALL NOT assume a legitimate no-op diff is zero-length, and SHALL still reject a zero-length carrier as `invalidCarrier`.
- AC-SDK-004-4 (duplicate delivery): WHEN a differential update is delivered to a replica more than once, THE SYSTEM SHALL leave the replica's observable state deeply equal after the second (and subsequent) deliveries as after the first (idempotent).
- AC-SDK-004-5 (restore-then-sync): WHEN a replica is restored from a saved full-state export, then exports its state vector and exchanges differential updates with a peer that made disjoint edits, THE SYSTEM SHALL converge both to deeply equal structured snapshots with all nonconflicting edits preserved.
- AC-SDK-004-6: THE SYSTEM SHALL keep the existing full-state export (`Y.encodeStateAsUpdate(doc)` with no state vector) available and unchanged; differential export is additive, not a replacement.

### REQ-SDK-005 — Lifecycle notifications derived from key deltas, with origin tagging and no feedback loop

A replica exposes subscriptions that UI and future persistence need: notification of local changes, notification of imported (remote) changes, an unsubscribe function, and defined behavior on destroy. Every mutation runs inside a Yjs transaction tagged with an origin. An **observable change** is derived from the transaction's actual key delta across **both** top-level maps (`root` and `ghostsync:records:v1`), read via `transaction.changed.get(map)`, not from whether `afterTransaction` fired; a transaction yields **at most one** notification regardless of how many maps it touched, and a no-op notifies zero subscribers even though Yjs fired `afterTransaction` once. A listener that throws cannot be mistaken for a malformed update.

**Acceptance criteria**

- AC-SDK-005-1 (local change): WHEN a local `set`/`delete`/collection write changes at least one leaf key in either top-level map, THE SYSTEM SHALL invoke every active change subscriber once for that transaction with an event whose `origin` is `local`.
- AC-SDK-005-2 (remote change): WHEN an update applied via `applyUpdate` changes at least one leaf key in either top-level map, THE SYSTEM SHALL invoke every active change subscriber once for that transaction with an event whose `origin` is `remote`.
- AC-SDK-005-3 (no feedback loop): WHEN a subscriber re-exports and re-broadcasts, THE SYSTEM SHALL carry the transaction `origin` on every notification so the subscriber re-broadcasts **only when `event.origin === "local"`** (it already holds the bytes for a `"remote"` event), so applying a remote update does not trigger a re-broadcast that loops. A test SHALL demonstrate a bounded exchange terminates, and SHALL pin the termination mechanism by asserting that an already-known remote apply changes no key and therefore fires **zero** notifications (per AC-SDK-005-6) — the exchange provably reaches a fixpoint rather than coincidentally halting after N rounds.
- AC-SDK-005-4 (unsubscribe): WHEN the function returned by `subscribe` is called, THE SYSTEM SHALL stop invoking that subscriber for all subsequent changes while leaving other subscribers active.
- AC-SDK-005-5 (destroy): WHEN `destroy()` is called, THE SYSTEM SHALL remove all subscribers and release the `Y.Doc`; AND WHEN `subscribe` or any other operation except `destroy` is called after `destroy()`, THE SYSTEM SHALL throw the baseline destroyed-replica error with its message unchanged — `Error("GhostSync Kit: replica has been destroyed")` (the exact string thrown by the real `#assertAlive` source); repeated `destroy()` SHALL be a safe no-op (baseline guarantee preserved).
- AC-SDK-005-6 (no-op application does not notify, derived from key deltas): WHEN an applied update or a local transaction changes **no** leaf key in **either** top-level map (a legitimate no-op diff, AC-SDK-004-3), THE SYSTEM SHALL NOT invoke change subscribers. THE SYSTEM SHALL derive this from the transaction's actual key delta — `transaction.changed.get(doc.getMap("root"))` and `transaction.changed.get(doc.getMap("ghostsync:records:v1"))` both undefined/empty — and SHALL NOT rely on the false claim that Yjs emits no transaction event for a no-op (applying an empty no-op update fires `afterTransaction` once and the `update` event zero times — defect C).
- AC-SDK-005-7 (subscriber exception isolation): WHEN a change subscriber throws, THE SYSTEM SHALL isolate the exception (wrap each listener dispatch) so one listener's failure neither stops other listeners nor changes the outcome of the `applyUpdate`/local write that triggered the notification, and SHALL NOT let a listener error be reported as a malformed update.

### REQ-SDK-006 — Transport-neutral update contract

The Kit defines a small, transport-neutral update contract that a later file transport and QR transport can both consume, without this milestone building any transport, capsule encoding, checksum, size bound, or UI. The contract carries the logical `documentId`, the raw Yjs `bytes`, and a `kind` discriminator — `"full"` or `"diff"` on a `TransportUpdate`, `"stateVector"` on a `StateVector`.

**Acceptance criteria**

- AC-SDK-006-1: THE SYSTEM SHALL define a `TransportUpdate` type `{ documentId: string; kind: "full" | "diff"; bytes: Uint8Array }` and a `StateVector` type `{ documentId: string; kind: "stateVector"; bytes: Uint8Array }`, each a plain serializable value with no transport-specific fields.
- AC-SDK-006-2: WHEN a replica exports full state, a differential update, or a state vector, THE SYSTEM SHALL return a value of the corresponding contract type with the correct `kind` and a non-empty `bytes`.
- AC-SDK-006-3: THE SYSTEM SHALL keep file capsule encoding, QR encoding, checksums, payload size bounds, and transport UI out of this milestone, and SHALL document them as the capsule/transport tier's responsibility that will consume this contract later.
- AC-SDK-006-4: THE SYSTEM SHALL keep the existing baseline carrier `{ documentId, bytes }` acceptable at `applyUpdate` (a `TransportUpdate` is a structural superset that still satisfies the baseline carrier shape), so existing consumers and tests keep working unchanged; BUT a `StateVector` (`kind:"stateVector"`) and any unknown explicit `kind` SHALL be rejected at `applyUpdate` before its bytes are treated as a Yjs update (REQ-SDK-007).

### REQ-SDK-007 — Validation, state-vector/update boundary, and rejection guarantees

The SDK defines, for each input class, which layer validates it and what a rejection guarantees about the live document. Adapter/schema validation is the consumer-facing layer; carrier/document-identity/kind validation is the engine boundary; malformed foreign bytes are bounded explicitly. A `StateVector` is a future transport message and untrusted at the boundary, never assumed same-process. Validation is separate from sender authentication. Applying foreign bytes is staged so a rejected or malformed update cannot leave the live document partially mutated, with guarantees bounded honestly.

**Acceptance criteria**

- AC-SDK-007-1 (local-write validation): WHEN a collection write produces a non-scalar field value or fails the adapter's `validate`, THE SYSTEM SHALL reject the write by throwing before mutating the live document, leaving observable state unchanged.
- AC-SDK-007-2 (adapter/schema compatibility): WHEN a collection is opened with an adapter whose `app`/`schemaVersion`/`entityType` does not match the collection's recorded `SchemaIdentity` (REQ-SDK-003 AC-SDK-003-2), THE SYSTEM SHALL reject the operation with a distinguishable `Error` and SHALL NOT mutate the document; this check SHALL work after export/restore and after remote import, not only on first process-local open. Furthermore, the compatibility check SHALL run BEFORE EVERY public `Collection<T>` operation — `put`, `get`, `getResult`, `list`, `listResults`, `delete`, and `has` — so a handle opened at one version rejects with the same schema-mismatch `Error` on its NEXT operation once a causally-newer incompatible meta arrives (a mismatch is never degraded into an `absent`/`undefined` or `invalidRecord` result, and a delete through an incompatible handle neither mutates nor notifies). The parsed meta value SHALL itself be validated before comparison, so a corrupt persisted meta (non-string, unparseable, `null`, a non-object, or a missing/mistyped field) yields a controlled schema error rather than a crash or a silent pass. (Correction round: the prior read/enumeration/delete paths did NOT recheck; this ADDS the recheck to them.)
- AC-SDK-007-3 (document mismatch): WHEN an update carrier's `documentId` does not equal the replica's `documentId`, THE SYSTEM SHALL reject it with `{ ok: false, reason: "documentIdMismatch" }` before decoding any bytes, leaving observable state unchanged (baseline guarantee preserved).
- AC-SDK-007-4 (kind boundary at `applyUpdate`): WHEN a carrier passes shape and document-identity checks but carries `kind:"stateVector"` or any unknown explicit `kind`, THE SYSTEM SHALL reject it with `{ ok: false, reason: "invalidCarrier" }` BEFORE treating its bytes as a Yjs update (a shared `{ documentId, bytes }` shape does not make state-vector bytes into update bytes); a carrier with no `kind`, `kind:"full"`, or `kind:"diff"` SHALL proceed to decoding.
- AC-SDK-007-5 (malformed update, bounded): WHEN a carrier passes shape, document-identity, and kind checks but its `bytes` are malformed/truncated Yjs bytes, THE SYSTEM SHALL guard the live merge so that IF it throws the live document's observable state is left unchanged and `{ ok: false, reason: "malformedUpdate" }` is returned with no notification. THE SYSTEM SHALL NOT assume `Y.applyUpdate` rolls back automatically on failure, and SHALL NOT rely on an unverifiable claim that the live apply cannot throw. The implementation captures a committed pre-apply snapshot (`Y.encodeStateAsUpdate(doc)`), detaches the change observer so no partially-mutated mid-throw state can be dispatched to subscribers, applies the foreign bytes directly to the live document under `try/catch`, and on a throw REBUILDS the live document from the snapshot (snapshot-rollback, see AC-SDK-007-6).
- AC-SDK-007-6 (snapshot-rollback recovery, honestly bounded): THE SYSTEM SHALL implement the live merge so a rejected/throwing apply cannot leak intermediate changes to subscribers and cannot leave a partial mutation observable: the engine SHALL detach its change observer for the raw apply (so subscribers see either the fully-committed new state or no change at all), and on a throwing apply SHALL rebuild the committed document from the pre-apply snapshot, destroy the discarded (possibly partially-mutated) document, reattach its observer, and preserve all active subscriptions and previously-returned `Collection` handles (which resolve the committed document lazily). THE SYSTEM SHALL state honestly that this guarantees the **observable projection** is deep-equal to the pre-call projection on any `ok:false`, and SHALL NOT claim unconditional rollback of arbitrary internal Yjs state merely because the JSON projection was restored. Pending out-of-order Yjs updates ARE preserved (Yjs 13.6.33 `encodeStateAsUpdate` serializes pending structs/ds, so the rollback snapshot carries them, and on the success path the bytes are applied to the live document directly) — VERIFIED by a dependency regression (a later update delivered before its prerequisite, across an intervening apply, converges with no edit lost).
- AC-SDK-007-7 (rejection guarantee stated): THE SYSTEM SHALL document that a rejected `applyUpdate` (any `ok: false` — invalid carrier, wrong/stateVector/unknown kind, document mismatch, or staged-merge throw) guarantees the live document's observable projection is deep-equal to its pre-call projection, and fires **no** change notification; a successful `applyUpdate` (`ok: true`) guarantees the bytes decoded and were merged. The guarantee is over the observable projection, bounded as in AC-SDK-007-6.
- AC-SDK-007-8 (exportDiff carrier rejection): WHEN `exportDiff` is given a value that is not a well-formed `StateVector` for this document, THE SYSTEM SHALL reject it with a stable, distinguishable reason — malformed carrier shape (`invalidStateVector`), wrong `documentId` (`documentIdMismatch`), wrong `kind` (`invalidStateVector`), or encoded state-vector bytes that fail to decode (`invalidStateVector`) — and SHALL NOT mutate the document and SHALL NOT fire a notification. A valid no-op diff (peer already synchronized) is non-trivial non-empty Yjs bytes, not zero-length.
- AC-SDK-007-9 (validation ≠ authentication; bounded scope): THE SYSTEM SHALL document that all of the above is integrity/shape/identity validation and NOT sender authentication, and SHALL state explicitly what imported-data validation is in scope now (carrier shape, document identity, kind, decodability via the staging merge, size bounded before decode at the capsule tier) versus deferred (payload size bounds, capsule version checks, checksums, and adapter-level field validation of foreign bytes — a peer could introduce a field the local adapter would reject on a local write; this is a stated, bounded limitation, not silently ignored).

## Non-functional requirements

- **NFR-SDK-001 — Browser compatibility (requirement; static check only, execution evidence pending).** The Kit `src` SHALL contain no `node:` imports and SHALL compile with `lib: ["ES2022"]` and no `DOM` lib, so the emitted library is usable in a browser bundle. Note: `packages/kit/tsconfig.json` sets `types: ["node"]`; this is a **type-checking-only** convenience (the proof suite runs on Node) and introduces **no runtime `node:` dependency into the emitted `dist`**. A `no-node-imports` source scan over `src` (test 9.16) is a **static check** of this requirement — it is NOT proof of browser runtime compatibility and the system SHALL NOT be described as "guaranteed browser-compatible". The compatibility requirement is precisely "no `node:` imports, library compiled without DOM libs"; actual browser-executed evidence is **pending/future work**. The proof suite stays Node in-memory.
- **NFR-SDK-002 — Offline behavior.** Every requirement SHALL be demonstrable with no network; the suite runs entirely in-memory in Node.js; concurrent offline entity creation (AC-SDK-002-4) is demonstrated without any server or pre-sync.
- **NFR-SDK-003 — Deterministic test output.** Runs SHALL print actual pass/fail counts; property tests SHALL use seed `424242`, 200 runs, and report `seed`/`numRuns`/`numSkips`/`numShrinks` from the real `RunDetails` via the existing `tests/fc-report.ts` reporter.
- **NFR-SDK-004 — Strict TypeScript, versioned API.** No `any` by default; public interface versioned and documented; internals private; no new runtime or dev dependency added (Yjs/Vitest/fast-check/TypeScript only). Adding a discriminated-union variant (e.g. `ApplyOutcome` gaining `"malformedUpdate"`) SHALL be recorded as a potential **minor breaking change for exhaustive consumers** (a consumer `switch` with no `default` must add a case), not described as universally source-compatible.
- **NFR-SDK-005 — Preserve existing regression coverage.** The 37 existing tests and six fast-check properties SHALL remain in scope, unedited, and keep passing; all new work is additive. Any refactor of `src` to support the structured model SHALL keep the existing public `createKit().createReplica(...)` contract working, SHALL keep `getState()` as the flat baseline projection of **every** `root` key (no filtering, no key reserved or rejected), and SHALL keep the legacy flat fields in the existing `root` `Y.Map` with its baseline encoded structure unchanged (structured records live in a separate top-level `ghostsync:records:v1` map; no independently-created nested map per replica). A FIXTURE test SHALL restore bytes produced by the baseline `ab37419` build and assert the baseline projection round-trips.
- **NFR-SDK-006 — No secrets or PII.** No keys, tokens, or personal data in the repo, commits, or build output.

## Out of scope for this milestone

- IndexedDB persistence, service workers, and offline app loading (separate concerns per architecture steering; the restore-then-sync path is the in-memory surrogate for persistence-after-reload).
- File capsule format, QR (small/animated), checksums, and payload size bounds (capsule/transport tier; this milestone only defines the transport-neutral contract they will consume).
- Transport UI and any app screens (FieldLedger/PatchBoard/Studio UI). Adapter examples in `design.md` are code-level consumer illustrations, not app UI.
- Sender authentication (a checksum detects corruption, it does not authenticate; documented, not implemented).
- Adapter-level field validation of **foreign** incoming bytes (bounded limitation, AC-SDK-007-9), and deferred application business rules (only structural scalar-type/shape validation is in scope now).
- Nested/rich collaborative values beyond scalar fields (Y.Text, Y.Array inside a field) — fields stay scalar in this milestone.
- Actual browser-executed evidence (NFR-SDK-001 is a static build-time check only; execution evidence is pending).

## Documented limitations (explicit)

- **Same-field LWW** keeps exactly one submitted value; the losing concurrent value is discarded (AC-SDK-002-3).
- **Reused-deleted-id** is supported (recommended policy: reuse allowed); a field concurrently deleted and rewritten resolves by native Yjs LWW (AC-SDK-002-7).
- **Schema business rules** beyond structural scalar validation are deferred to the application tier (AC-SDK-007-9).
- **Browser execution** evidence is pending; only the static no-`node:`-imports / no-DOM-lib check is in scope (NFR-SDK-001).
- **Rollback guarantees** are over the observable projection and are honestly bounded; a full-state snapshot is not assumed to capture every pending out-of-order Yjs update (AC-SDK-007-6).
- **`ApplyOutcome` union growth** is a potential minor breaking change for exhaustive consumers (NFR-SDK-004).

## Assumptions

- The structured model keeps the legacy top-level `root` `Y.Map` untouched and stores structured entity fields as **flat composite leaf keys** in a **separate** top-level `Y.Map` named `ghostsync:records:v1` in the same `Y.Doc`; the baseline flat scalar-map public API (`set`/`delete`/`get`/`has`/`getState` on the replica) is preserved exactly because legacy keys stay in `root` and `getState()` projects every `root` key (map membership keeps structured keys out — no key-shape predicate, no reserved prefix, no rejected key). No independently-created nested `Y.Map` is used, per defect A. This is the collision-free addressing model; see `design.md` § Storage layout.
- Yjs `13.6.33` (already pinned) provides `encodeStateVector`, `encodeStateAsUpdate(doc, sv)`, `applyUpdate`, and `mergeUpdates`; verified present in the installed package. No new dependency is required.
- The independent reviewer reproduced defects A/B/C with Yjs `13.6.33`; the corrected model (flat composite keys; changed-fields `put`; key-delta-derived notifications) is designed to be consistent with those reproductions.
